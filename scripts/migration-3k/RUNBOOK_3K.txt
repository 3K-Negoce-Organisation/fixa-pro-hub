Migration 3K-Négoce — enchaînement recommandé
==============================================
Synthèse « fait / reste » : MIGRATION_STATUS_3K.txt
Vérification rapide Supabase + Railway + fichier VITE : ./scripts/migration-3k/verify-migration-3k-state.sh

Références projets Supabase 3K : voir SUPABASE_3K_REFS.txt (mots de passe uniquement dans .generated/).

Sécurité : ne jamais coller les sbp_… dans un chat public ; régénérer les tokens après migration.


Les jetons compte 3K ne doivent pas être collés dans le chat : exportez-les dans votre terminal.

0) Prérequis locaux
   - supabase CLI, railway CLI, jq, openssl
   - Dumps variables Railway déjà possibles : ./dump-luceka-vars.sh (compte perso)

1) Supabase — créer les 3 projets sous l’org 3K
   - Récupérer l’UUID de l’organisation : dashboard Supabase (compte 3K) → Organization settings / URL.
   - export SUPABASE_ACCESS_TOKEN_3K='sbp_...'
   - export SUPABASE_ORG_ID_3K='...'
   - ./scripts/migration-3k/bootstrap-supabase-3k.sh
   - Attendre ~1–2 min si link échoue tout de suite.

2) Schéma (migrations)
   - ./scripts/migration-3k/apply-migrations-3k.sh
   - Ordre : migrations fixa-pro-hub puis admin-hub-central pour chaque ref.
   - En cas de conflit SQL entre les deux dépôts, résoudre à la main (migrations rarement dupliquées).

3) Edge functions
   - ./scripts/migration-3k/deploy-functions-3k.sh

4) Secrets edge
   - ./scripts/migration-3k/generate-edge-secrets-3k.sh
     (SUPABASE_* + STRIPE_SECRET_KEY / VAB_API_KEY depuis .railway-dump/ si présent)
   - cp scripts/migration-3k/secrets-edge.manual.example.env scripts/migration-3k/.generated/secrets-edge.manual.env
   - Remplir RESEND, ORDER_UPDATE, STRIPE_WEBHOOK_SECRET, N8N_WEBHOOK_URL (copie depuis anciens projets
     Supabase → Edge secrets, compte ayant accès aux refs LEGACY_SUPABASE_REFS.txt).
   - Optionnel : .generated/secrets-edge.manual.production.env pour surcharges (ex. webhook Stripe live).
   - ./scripts/migration-3k/apply-edge-secrets-3k.sh
     (export APPLY_EDGE_SECRETS_FORCE=1 pour ignorer la validation des clés manuelles)
   - Les clés SUPABASE_* dans les fichiers générés sont ignorées par la CLI au moment du set
     (réservées / gérées par la plateforme) ; elles apparaissent quand même dans Dashboard → Secrets.

5) Données
   - Anciens refs : LEGACY_SUPABASE_REFS.txt
   - cp scripts/migration-3k/legacy-db.passwords.env.example scripts/migration-3k/.generated/legacy-db.passwords.env
   - Remplir LEGACY_DB_PASSWORD_* (mot de passe DB de chaque ancien projet)
   - Pour chaque env : ./scripts/migration-3k/sync-public-columns-from-legacy.sh <develop|staging|production>
     (aligne les colonnes public.* manquantes avant le dump)
   - Truncate public (optionnel si base déjà propre) puis :
     ./scripts/migration-3k/dump-restore-data-3k.sh [--only develop|staging|production]
   - Schéma public uniquement ; pas auth.users ni Storage — voir STORAGE_BUCKETS_3K.txt

5b) Auth Supabase (manuel)
   - Voir AUTH_REDIRECTS_3K.txt (Site URL + Redirect URLs par projet 3K)

6) Railway 3K
   - Détail pas à pas : RAILWAY_SETUP_3K.txt
   - Mapping dumps JSON → envs / services : RAILWAY_DUMP_MAPPING_3K.txt
   - export RAILWAY_TOKEN_3K (voir railway-3k.env.example)
   - ./scripts/migration-3k/resolve-railway-workspace-3k.sh
   - ./scripts/migration-3k/generate-railway-vite-env-3k.sh → .generated/railway-vite-env.txt
   - railway link -p … sur 3k-Negoce_project ou ./scripts/migration-3k/railway-init-3k.sh pour un projet neuf
   - Services vides → ./scripts/migration-3k/create-railway-services-3k.sh (API GraphQL ; voir RAILWAY_SETUP_3K.txt)
   - Variables hors VITE depuis .railway-dump/ (RAILWAY_DUMP_MAPPING_3K.txt)

7) GitHub
   - Dépôts org déjà synchronisés : 3K-Negoce-Organisation/fixa-pro-hub et admin-hub-central
   - Brancher les nouveaux services Railway sur ces dépôts.

8) Post-migration
   - Stripe produits / webhooks manuels (compte 3K)
   - n8n : import workflows + credentials à la main
   - DNS OVH quand prêt
